# Lessons Learned

Corrections and patterns discovered during development. Claude reads this at the start of each `/dev-task` to avoid repeating mistakes.

## Entries

- **`drizzle-kit push` doesn't reconcile pgView selector changes — you must drop the view first.** When you modify a `pgView(...).as((qb) => qb.select({ ... }))` definition (adding/removing/renaming selectors), `drizzle-kit push` treats the view as unchanged and leaves the old view in place. The next query against the view will fail with `column "X" does not exist` because the runtime schema expects selectors the deployed view doesn't have. **Why**: drizzle-kit's diff logic for views is incomplete as of drizzle-orm 0.45.2 — it may detect the name is unchanged and skip the DROP/CREATE. **How to apply**: whenever you change the view's select list (not just add columns to a source table), run `DROP VIEW IF EXISTS <name>` directly against PG before `drizzle-kit push`. The next push will recreate the view fresh. Came up in Phase 14 Task 76 — the Phase 14 `extracted_content`/`extracted_at`/`extraction_status` columns were added to the view's selector but never landed in PG; the bug only surfaced when Phase 15's pg_dump/restore preserved the stale view and ranked.ts queries failed at runtime.
- **Start narrow, not broad** — user prefers focused scope over wide nets. Don't over-expand source lists, feature sets, or abstractions beyond what the current task explicitly asks for. **Why**: came up during early feed seeding when I tried to add dozens of tangentially-relevant sources; user wanted AI/LLM-only and to validate the core loop first. **How to apply**: when tempted to "also add X while I'm here," don't. Ship the narrower thing, learn, then expand.
- **One score, one thing** — don't reuse a dimension (e.g. `authority_score`) to solve two different concerns (ranking AND allocation). Each concern gets its own field, even when their defaults look identical. Came up in Phase 10: I initially proposed reusing `authority_score` for analyze batch allocation; user corrected with "one score one thing"; added dedicated `analyze_weight` instead. Coupling two concerns to one knob makes tuning one of them break the other.
- **The API is the product; every client (including web) is just a consumer.** All functionality lives behind REST endpoints — no business logic in Next.js server actions or route handlers, no pre-formatted strings in responses (raw ISO timestamps + raw numbers only), no state in the web app that doesn't originate in a GET. Zod schemas stay in `@homenews/shared` so any future TS client reuses them. Auth will eventually land at the API layer, not the web. **Why**: the architecture is explicitly heading toward server-to-server consumers (CLI, future iOS, Claude-as-a-tool calling `/search`). Any logic that leaks into the web client has to be reimplemented for every new consumer. **How to apply**: when tempted to compute a field in a server component "just for the dashboard," add it to the API response instead; when tempted to format a date string server-side, return ISO and format in the client; when building a new feature, ship and validate the API endpoint first (curl / Postman) *before* touching any UI.
- **Don't use the freshness signal for iteration order** — freshness is the right signal for *ranking* (which articles the user sees) but wrong for *cancel-fairness* (which articles get processed first in a batch). In Phase 10 I sorted the analyze batch by `COALESCE(published_at, fetched_at) DESC` after fair allocation; arXiv's hyper-fresh timestamps clustered at the top, so cancelling mid-run starved lab feeds despite the allocator being correct. Fix was round-robin interleaving across feed buckets in Phase 10.1. **Rule**: if two concerns happen to share the same ordering signal, it's a smell — different concerns deserve different mechanisms even if the signals look similar.
- **Env vars referenced in deploy config must be confirmed read by the code.** Phase 17 Task 108 found that `compose.yaml` and the Helm chart both wired `API_PORT=52001`, but `apps/api/src/index.ts` only read `process.env.PORT`. The compose stack silently bound port 3001 (the code default), and the latent mismatch would have blocked the k3s cutover via probe failures on container port 52001. **Why**: deploy configs and source code drift independently — a rename on one side leaves a phantom env var on the other that quietly does nothing. **How to apply**: when adding/changing an env var in `deploy/compose.yaml` or `deploy/chart/values.yaml`, immediately `grep -rn '<VAR_NAME>' apps/ packages/` to confirm at least one source file reads it. If you're trying to introduce a *new* convention (e.g. `API_PORT` to disambiguate from Next.js's `PORT`), land both ends in the same change. Symptom of the bug class: probes never go ready, or the service is reachable on an unexpected port.
- **Postgres `POSTGRES_DB` / `POSTGRES_PASSWORD` env vars are honored only at `initdb` time on an *empty* `PGDATA`.** Once data exists, env changes have no effect — restarting the pod with a new `POSTGRES_DB=homenews` after PGDATA was already initialized as `homenews_prod` will *not* create or rename the database. Same for password changes via env. **Why**: the official postgres entrypoint script checks for an empty data directory; if non-empty, it skips initdb entirely and just starts the server. **How to apply**: to rename or repassword a Postgres pod that already has data, either (a) `psql -c "CREATE DATABASE … OWNER …;"` + `DROP DATABASE …;` to rename (cheapest), (b) `psql -c "ALTER USER … WITH PASSWORD '…'"` to repassword, or (c) scale StatefulSet to 0, delete PVC, scale back to 1 to force fresh initdb (with selfHeal on, this fights ArgoCD — disable automated.selfHeal first or use option a/b). Came up in Phase 17 Task 114 when realigning cluster DB name to match legacy.
- **In-cluster apps must use Service DNS for peer-to-peer; only browser/external clients hit ingress hostnames.** Phase 17 cutover surfaced this in the web pod: `apps/web/src/lib/api.ts` used a single `process.env.NEXT_PUBLIC_API_URL` for both server-side rendering (running inside the pod) AND the client bundle (running in the user's browser). The shared value was `http://homenews-api.arch.local` — the public ingress hostname — which **doesn't resolve inside the pod** (no `/etc/hosts` entry, not a cluster DNS name). Result: SSR fetches failed silently, dashboard rendered empty even though the API was healthy and reachable via the ingress from any browser. **Why**: pod-to-pod inside k8s goes through `<svc>.<ns>` (or `<svc>.<ns>.svc.cluster.local`) cluster DNS — fast, one hop, never leaves the pod network. Hitting your own cluster's ingress from inside is wrong on two counts: (a) it doesn't resolve unless you add `hostAliases`, (b) even if it did, the request would go pod → node iptables → Traefik → ingress controller → Service → pod — a wasteful loop. **How to apply**: any time an app inside the cluster fetches another app inside the cluster, the URL goes through Service DNS. Reserve `NEXT_PUBLIC_*` and similar build-time-baked values for the *external* surface (browsers, mobile, public CLI). For Next.js specifically, the pattern is two env vars: `API_URL` (non-public, read at runtime, server-only — set to `http://<svc>.<ns>`) winning over the falling-through `NEXT_PUBLIC_API_URL` (inlined at build, browser-only — set to the public ingress URL). Audit at every migration: grep for absolute URLs in source + chart values, classify each as "calls another in-cluster service" (must be Service DNS) vs "user-facing" (ingress hostname).
- **`pg_dump -Fc <dbname>` does not transfer role definitions or passwords.** Database-level dumps include schema + data + extensions, but NOT `pg_authid` (which holds user/password rows). After `pg_restore` into a target cluster, the destination user keeps its own pre-existing password — set by `initdb` from the original `POSTGRES_PASSWORD` env. **Why**: roles are cluster-global; `pg_dump <dbname>` is scoped to a single database. Only `pg_dumpall` or `pg_dumpall --globals-only` walks `pg_authid`. **How to apply**: after a database-level pg_dump/pg_restore between clusters, run `ALTER USER <name> WITH PASSWORD '<new>'` on the target to align with whatever password the connecting clients expect. Symptom: `password authentication failed for user "..."` from the app pod immediately after a successful row-count-matching restore. Came up in Phase 17 Task 114 cutover.
